# Agent Note：JSON 发布状态不确定时的终止恢复

Status: implemented

[English](2026-08-21-storage-json-post-publish-durability-failure.md) | 中文

## 问题

POSIX 上，`rename()` 先让完整替换可见，父目录同步随后才证明崩溃持久性。`single` JSON 单元若在替换后回滚内存，就会持有旧状态，而介质已有新状态；下一次整文件写入可能静默覆盖该替换。`per-record` 单元没有缓存，但后端拒绝时，其领域仍保留旧缓存。旧格式初始化也会在 `loadAll()` 期间发布记录文档，并可能到达相同失败点。

可见性与持久性的区别也适用于 [Windows JSONL 发布](../../../../packages/session/session-persistence-jsonl/src/win32.ts)。可变 JSON 单元还需要在报告失败后，为仍存活的句柄规定安全处理规则。

## 决策

`writeAtomic()` 将成功替换后的目录失败分类为 `PublishedWriteDurabilityError`，保留原始原因。同时发生的目录句柄关闭失败不能替换同步错误。替换前的失败保留普通清理与回滚语义；临时文件清理尽力执行，不能替换原始失败。

两种 JSON 布局共用一个内部生命周期控制器。发布后失败会阻止新操作，排空已接纳的 I/O，仅释放后端打开名称一次，并以携带分类错误的 `StorageError('closed')` 拒绝。`single` 单元不在替换后恢复陈旧内存。`per-record` 单元对写入与旧格式初始化应用相同终止规则。重新打开会重读实际介质。

领域仅在具体 `KvUnit` 写入调用周围分类 `StorageError('closed')`。该拒绝使缓存读取与新写入立即失效。排队任务跳过调用方变换函数，写入链排空，设施在单元成功关闭后释放名称。失败操作等待资源销毁，不替换其原始错误；释放失败时名称仍被占用，并通过共用同一资源销毁的显式 `Domain.close()` 暴露。`update` 变换函数抛出相同错误仍属调用方失败；其他写入错误保持领域可重试。

JSON 格式、领域 schema、配置、包导出、依赖与公共 TypeScript 类型保持不变。现有 `closed` 代码表达终止句柄，无需添加公共错误代码。

## 验证

真实文件故障注入覆盖两种布局、记录替换、全局值替换、single 布局删除与 per-record 旧格式初始化。测试验证同时关闭失败时仍保留同步原因、拒绝旧句柄使用、立即重新打开，以及后续无关写入仍保留已发布值。发布前失败仍可重试。确定性生命周期测试通过屏障阻止资源销毁完成，让并发发布与显式关闭竞态发生，拒绝排队变换、抑制变更事件，并保持名称占用直到唯一一次资源销毁完成。调用方变换的负向对照保持健康领域可用。独立 POSIX 进程通过 Loader 与仅用于测试的 `cordis.yml` 启动存储插件，只注入目录同步失败，并验证两种布局的已发布文件与新领域读取结果。

## 备选方案

**回滚内存并保持句柄可用。** 介质已经暴露替换，下一次整文件写入可能将其抹除。

**把同步失败报告为成功。** 仅有可见性不满足后端的持久性承诺。

**保留新单元缓存，拒绝操作但不终止句柄。** 领域会保留旧缓存，使两个存活的拥有方持有不一致的值。

**发布旧状态作为补偿。** 第二次替换可能在相同同步步骤失败；没有日志就无法恢复事务确定性。

**把队列层的所有 `closed` 错误分类为后端失败。** 调用方变换函数可以抛出该错误，而后端并未终止。分类应在实际后端调用处进行。

## 影响

POSIX 发布后目录失败会终止受影响句柄，避免陈旧写入。恢复要求从介质重新打开，其中可能包含尚未确认崩溃持久性的替换。成功操作保留现有发布协议；发布前失败仍可重试。故障注入证明存活进程的一致性，不证明真实断电行为；Windows write-through 与现有部分旧格式初始化策略保持不变。
