# Agent Note: JSON 发布结果不确定时的终止恢复

Status: implemented

[English](2026-08-21-storage-json-post-publish-durability-failure.md) | 中文

## 问题

在 POSIX 上，`rename()` 会先使完整替换内容可见，随后父目录 `fsync()` 才能证明目录项变更具备崩溃持久性。JSON 存储 unit 把每次发布拒绝都当作发布前失败：即使 `rename()` 已替换文件，也会恢复内存中的修改。此时实时 unit 保存旧状态，介质保存新状态；unit 下一次发布整个文件时，可能用陈旧状态覆盖已可见的替换内容。

这个失败点与 [Windows JSONL 发布](../architecture/2026-07-05-windows-jsonl-durable-publish.md)记录的持久性区别相同，但可变的整文件 unit 还需要规定失败上报后的实时状态恢复方式。

## 决策

成功替换后若父目录同步失败，`writeAtomic()` 会将其分类为 `PublishedWriteDurabilityError`。如果目录句柄关闭同时失败，该失败不会取代作为 cause 携带的同步失败。替换前的失败保留普通清理和回滚语义。

JSON unit 收到这类发布后错误时，会在自身私有状态中保留已发布修改，进入终止关闭状态，等待已经开始的发布全部结算，释放后端打开 slot，并以 `StorageError('closed')` 拒绝，同时把分类后的错误作为 cause。任何调用方都不能再次读取或发布该 unit 中结果不确定的缓存状态。

领域只在具体 `KvUnit` 写入调用周围识别 `StorageError('closed')`。这种后端拒绝会立即使缓存读取和新写入失败；排队任务会跳过调用方转换函数，写入链排空，`unit.close()` 恰好完成一次，随后设施才释放领域名称。失败操作和排队操作会等待该拆除完成后再结算，显式 `Domain.close()` 共享同一个 promise。`update` 转换函数抛出相同公共错误代码时仍属于调用方失败，不会终止健康 unit。其他写入失败仍可恢复：领域内存保持不变，之后排队的写入继续执行。

JSON 文档格式、领域 schema、配置、包导出、依赖和公共 TypeScript 类型均不变化。现有 `closed` 代码可以表达句柄的终止状态，无需增加公共错误代码。

## 验证

真实文件故障注入会先替换目标，再使父目录同步和句柄清理失败；测试证明同步错误仍是根本原因、旧 unit 会关闭、目标保留新值、新 unit 能重新加载该值，之后成功发布也会保留该值。领域测试用屏障阻塞终止 unit 的清理，证明缓存读取和排队写入都会停止、设施名称会保留到唯一一次拆除完成、不发出变更事件，并能重新打开同一领域。一个负向对照从 `update` 转换函数抛出 `StorageError('closed')`，证明领域仍然可读、可写且名称保持占用。现有发布前失败覆盖继续区分可恢复的回滚路径。

## 备选方案

**回滚内存并保持 unit 可用。** 这会重现缺陷：介质已经公开替换内容，下一次整文件写入可能将其静默删除。

**把目录同步失败报告为成功。** 后端承诺调用 resolve 时已达到持久状态。可见性不能证明崩溃持久性，因此 resolve 会在不告知调用方的情况下削弱该承诺。

**保留 unit 的新内存但拒绝写入。** 领域仅在后端成功后更新自身缓存，因此仍会保留旧值。两份实时缓存依旧不一致，之后的领域写入无法安全调和它们。

**再次发布旧状态作为补偿。** 第一次替换已经越过可见点，补偿替换也可能在同一个目录同步步骤失败。没有日志时，第二次发布无法恢复事务确定性。

**把离开领域队列的每个 `StorageError('closed')` 都分类为后端失败。** 排队任务还会运行调用方提供的 `update` 转换函数，该函数可以抛出相同的公共错误类型而不改变 unit 生命周期。分类必须放在拥有终止状态的具体后端调用周围。

## 影响

罕见的 POSIX 目录同步失败会使受影响的 unit 和领域句柄进入明确的终止失败状态，不再允许静默覆盖数据。恢复需要从介质重新打开；介质可能包含完整替换内容，但其崩溃持久性尚未得到证明。替换前的普通失败仍可重试，成功写入的现有行为和成本不变。
