# Agent Note：Win32 文件夹路径按 UTF-16 码元终止

Status: implemented

[English](2026-08-21-win32-folder-path-utf16-termination.md) | 中文

## 问题

Win32 原生目录选择器以 NUL 终止的 UTF-16LE 字符串接收 `IShellItem` 显示名称。直接内存解码器原本在码元低字节为零时就停止，而不是等待完整的 `0x0000` 终止符。因此，`阀`（`U+9600`）等合法字符会让所选路径在工作区采用前被截断，而大多数 ASCII 和 CJK 路径会掩盖该缺陷。

[Win32 文件夹对话框决策](../feature/2026-08-02-win32-in-process-folder-dialog.md)拥有由 koffi 支持的 COM 实现。本 Agent Note 只拥有该实现所返回显示名称的解码。

## 决策

解码器以完整的双字节 UTF-16LE 码元前进，只在当前码元的两个字节均为零时终止。它继续直接查看原生分配，因为 koffi 的 `void **` 出参暴露的是原始地址，无法安全使用会解引用指针的字符串解码。

选择 fixture 包含一个 UTF-16LE 低字节为零的字符。内存释放、COM 对象释放和 COM 反初始化仍属于同一回归，从而保证路径正确性不会削弱原生资源清理。

## 考虑过的替代方案

- **任一字节为零时停止。** UTF-16 的非 NUL 码元任一字节都可能为零，因此该方式无法区分文本与终止符。
- **使用 `koffi.decode(address, 'str16')`。** 该值是通过出参取得的原始地址；将其当作指针容器会增加一次解引用，并可能让对话框进程崩溃。
- **限制或规范化所选路径。** 操作系统已经返回合法绝对路径。修改用户数据只会掩盖解码器缺陷，并拒绝普通 Windows 名称。

## 后果

Windows 文件夹选择会保留完整 UTF-16 路径，包括低字节为零的字符。RPC 值、工作区身份规则、COM ABI、原生分配生命周期和其他平台选择器均不变化。解码仍在既有的有界内存视图内扫描。

## 测试

模拟 koffi COM 测试选择 `C:\疏水阀数据\2025年\子目录`，其中 `阀` 码元包含字节序列 `00 96`。测试钉住完整结果，以及显示名称分配、shell item、dialog 与 COM apartment 的释放。既有对话框测试继续覆盖取消与提取失败。
