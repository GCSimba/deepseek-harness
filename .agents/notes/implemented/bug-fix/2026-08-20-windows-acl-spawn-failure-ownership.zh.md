# Agent Note：Win32 spawn 句柄的事务性所有权

Status: implemented

[English](2026-08-20-windows-acl-spawn-failure-ownership.md) | 中文

## 问题

Windows ACL launcher 会跨越多个可能失败的原生边界，而此时所有权可能只完成了部分组装：三个匿名管道对、调用方所拥有 stdio 句柄上的临时继承状态、进程与线程句柄、kill-on-close job，以及转交给管道排空和进程等待操作的句柄。任何失败都可能发生在只取得其中一部分资源之后。在捕获 `GetLastError` 前清理资源还可能替换首个诊断。如果没有明确的所有权边界，这些路径可能遗留原生句柄、让 stdio 在无关的后续 spawn 中保持可继承、搁置部分创建的子进程，或报告清理错误而非真正失败的操作。

## 决策

`spawn.ts` 以事务方式持有每项原生资源，直至完整返回把所有权转交给调用方。管道式 spawn 设置把三个管道对的创建和配置视为一个整体，失败时关闭所有已经取得的管道对；如果 `CreatePipe` 返回畸形的成功结果，则关闭其中存在的非空半边。进程创建成功后，只有在进程信息中的两个句柄都有效时，才把进程句柄和输出读取句柄转交给调用方。如果进程信息结果不完整，launcher 会在进程句柄存在时终止该进程，并在拒绝结果前关闭每个已返回的原生句柄。

继承 stdio 的 spawn 会持有 kill-on-close job，直至完整的子进程结果返回。它只记录继承位已经成功启用的 stdio 句柄，并在 `finally` 边界中精确恢复这组句柄。部分进程信息结果采用相同的终止与关闭处理；job 分配或线程恢复失败时，会释放挂起的子进程以及所有仍由本地持有的句柄。

管道排空和进程等待接收其传入句柄的所有权，并在 `finally` 中关闭句柄，包括失败出口。每个首要 Win32 失败都会在尽力清理开始前转换成 `Win32Error`，或先捕获其数值错误码。清理调用的返回值不会替换首要错误。这些规则保留在 Windows ACL spawn 实现内部，不新增公共句柄所有者抽象。

## 验证

公共入口测试在管道获取、管道继承、stdio 继承、进程创建、畸形进程信息、job 分配、线程恢复、管道探查/读取、进程等待和退出码查询处注入失败。测试断言精确的首要 Win32 错误码、每个已启用继承位的恢复、已返回部分进程的终止，以及每个本地所有句柄的关闭。同一套件还覆盖成功时的所有权转移、命令行引用和顶层沙盒失败路径；`spawn.ts` 的定向覆盖率包含每条语句、分支、函数和代码行。

## 备选方案

**引入通用的原生句柄 RAII 框架。** 不予采用，因为这些所有权形态数量有限且局限在一个模块中。框架会扩大包表面、掩盖不同的转移点，却不能改善这些路径。

**依赖进程退出回收泄漏的句柄或继承状态。** 不予采用，因为 runner 和宿主的生命周期足以让泄漏和可继承句柄影响后续启动，而部分创建的挂起子进程可能无限期存活。

**让清理失败替换原始失败。** 不予采用，因为首个失败操作才指明可采取行动的原因；该诊断物化后，清理保持尽力而为。

**只保护 `CreateProcessAsUserW` 失败。** 不予采用，因为所有权从管道或 stdio 设置阶段开始，并持续到排空与等待；进程创建前后的失败遵循相同的资源生命周期契约。

## 影响

在每个经过测试的出口，原生句柄和临时继承状态都只有一个本地所有者，畸形进程结果也无法留下仍在运行的已返回子进程。清理调用即使改变 last-error 状态，也不会破坏首要 Win32 诊断。成功 spawn 的行为、包导出、TypeScript 接口、配置和子进程 I/O 契约均不变化。清理 API 的返回值仍刻意按尽力而为处理；launcher 保证尝试每项由其负责的清理，而不保证 Windows 接受每次清理调用。
